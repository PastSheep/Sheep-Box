# 项目 Git 协作规范



> 本文档作为《Python 项目编程规范》的配套约定，用于统一团队 Git 使用方式，降低协作冲突、保证历史清晰、规范评审流程。适用于项目内所有参与开发人员。



## 1 总则



### 1.1 目标

1. 保证主干（`main`/`master`）长期可发布、可回滚

2. 分支命名统一、生命周期清晰，避免分支混乱

3. Commit 信息规范、可追溯，便于 code review 和问题定位

4. 评审（CR）流程标准化，代码质量有把关



### 1.2 核心原则

1. **主干稳定**：`main` 分支始终处于可发布状态，任何时刻禁止直接往 `main` 推未评审代码

2. **小步提交**：功能拆小、提交频繁，禁止一个大功能攒一个巨型 commit

3. **评审必经**：除极小修复外，一切合并到 `main` 的代码必须经过 Code Review

4. **可回滚**：任何提交都要保证可以单独回滚，不留夹带改动



## 2 分支策略（推荐：GitHub Flow 简化版）



采用 **主干开发 + 短生命周期特性分支**，适合中小团队快速迭代：



```text

main（长期稳定，可发布）

 ├── feature/xxx（新功能，从 main 拉出）

 ├── fix/xxx（缺陷修复，从 main 拉出）

 └── release/x.y.z（发布分支，视需要）

```



### 2.1 分支类型



| 分支 | 命名 | 生命周期 | 说明 |

|---|---|---|---|

| 主干 | `main` | 长期 | 始终可发布，禁止直接提交 |

| 特性 | `feature/<描述>` | 短（功能合并即删） | 新功能开发 |

| 修复 | `fix/<描述>` | 短（修复合并即删） | bug 修复、hotfix |

| 发布 | `release/<版本号>` | 中 | 大版本收敛、打 tag 用，视团队需要 |



命名示例：`feature/user-login`、`fix/payment-timeout`



### 2.2 分支规则

1. 功能分支从 `main` 的最新提交拉出

2. 分支只在开发、评审阶段存活，合并后**立即删除**

3. 禁止在 `main` 上直接开发、禁止跨功能分支互相长期依赖

4. 分支尽量短小，超过预期工时主动拆分或与 main 同步

5. 多人协作同一功能时，统一推到同一 feature 分支，各自拉最新后再提交



### 2.3 版本管理（Tag）

1. 每次正式发布，在 `main` 打 tag：`v1.2.0`（语义化版本）

2. Tag 命名统一：`v<主版本>.<次版本>.<补丁>`



## 3 Commit 规范



### 3.1 提交信息格式（强制统一）

采用 **Conventional Commits** 简化版，格式：



```text

<type>(<scope>): <subject>

```



- `type`：提交类型（见下表）

- `scope`（可选）：影响范围，如 `user`、`order`、`config`

- `subject`：一句话描述，**用中文**，简洁说明「做了什么」，以动词开头，控制在 50 字内



### 3.2 type 类型表



| type | 含义 |

|---|---|

| `feat` | 新功能 |

| `fix` | 缺陷修复 |

| `docs` | 文档变更 |

| `refactor` | 重构（不改功能） |

| `style` | 格式调整（不改变逻辑） |

| `test` | 测试相关 |

| `chore` | 构建、依赖、工具等杂项 |

| `perf` | 性能优化 |

| `ci` | CI 配置变更 |



示例：



```text

feat(user): 新增用户登录接口

fix(order): 修复超时未返回时的空指针

docs(readme): 补充本地启动步骤

refactor(common): 抽取统一的异常处理工具

```



### 3.3 Commit 纪律

1. **一次提交只做一件事**，禁止夹带无关改动

2. **不提交调试残留**（print、临时文件、断点）

3. 提交前必须自查：代码是否符合编程规范、是否通过本地校验

4. 严禁提交：密钥、密码、本地环境配置、编译产物、日志文件

5. 禁止用 `git commit --amend` 覆盖他人已评审/已推送的提交；本地未推送的 amend 可用

6. 禁止 `git push --force` 到共享分支（如需重写历史，必须组内对齐）



## 4 文件忽略（.gitignore）

1. 必须维护好 `.gitignore`，禁止提交：

 - 虚拟环境（`.venv/`、`venv/`）

 - 密钥与本地配置（`*.env`、`config/local*`）

 - 编译/缓存产物（`__pycache__/`、`*.pyc`、`.pytest_cache/`）

 - 本地 IDE 配置（`.idea/`、`.vscode/` 按团队约定）

 - 日志、临时文件（`*.log`、`*.tmp`）

2. 新增忽略规则要及时同步到 `.gitignore` 并提交



## 5 合并与 Code Review（CR）规范



### 5.1 提交流程

1. 开发完成 → 本地自查 → 推送 feature 分支 → 发起 Merge Request / Pull Request

2. MR 描述填写：**需求说明、改动点、自测情况、关联 issue**

3. 指定至少 **1 名** 评审人，核心模块建议 2 名



### 5.2 CR 检查项（评审人重点看）

- 是否符合《Python 项目编程规范》（格式、命名、类型注解、异常处理）

- 是否符合日志约定、是否遗漏异常日志、是否打印敏感信息

- 是否有重复代码、复杂度过高的函数

- 是否有明显性能问题、资源未释放

- 是否覆盖了必要测试

- 是否夹带无关改动、是否误提交敏感文件



### 5.3 合并规则

1. 必须通过全部评审意见、解决所有评论后才能合并

2. 合并前保证分支基于 `main` 最新（无冲突）

3. 合并方式：默认 **Squash Merge**（将特性分支压缩成一个 commit，保持主干历史干净）

4. 合并后立即删除功能分支



## 6 协作日常约定



### 6.1 拉取与同步

1. 每天开工先 `git pull` 同步 `main` 最新

2. 开发前从最新 `main` 拉分支，避免长期落后导致大量冲突

3. 解决冲突时：以 `main` 为准，自己的改动覆盖上去，解决后及时提交



### 6.2 职责边界

1. 未经授权不修改他人正在开发的分支

2. 不擅自合并他人未完成的 MR

3. 涉及公共模块、底层框架的改动，必须提前在组内说明



## 7 红线清单（强制禁止）

1. 直接向 `main` 提交未评审代码

2. 提交密钥、密码、本地配置、敏感文件

3. 夹带无关改动（一个 commit 混多个功能）

4. 提交调试残留、死代码、无用文件

5. `push --force` 到共享分支（未经对齐）

6. 回滚/重写已推送且他人依赖的历史



## 8 附则

1. 本规范为项目强制规范，与《Python 项目编程规范》《项目日志 Logger 约定》配套执行

2. 存量不合规的分支、commit 逐步整改，新增内容严格遵守

3. 分支策略、合并方式如需调整，需组内统一对齐后更新文档

4. CI 接入后，合并门槛以 CI 校验结果为准（格式检查、类型检查、测试）
