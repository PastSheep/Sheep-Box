# Python 项目编程规范



## 1 总则



### 1.1 规范目的

为统一本项目代码风格、编码逻辑、工程写法，提升代码可读性、可维护性、一致性，降低团队协作沟通成本、减少 BUG、统一 CR（代码评审）标准，特制定本规范。



本规范适用于本项目**所有 Python 业务代码、工具脚本、单元测试代码**，所有项目参与开发人员必须严格遵守。



### 1.2 规范依据

以 Python 官方 PEP 系列标准为基础，结合工业界现代 Python 工程最佳实践：

- PEP 20：Python 设计哲学（Pythonic 核心原则）

- PEP 8：代码风格规范

- PEP 257：文档字符串规范

- PEP 484 / PEP 585：类型注解规范

- 现代工程工具：Black、Ruff、Mypy、Pre-commit 自动化规范体系



### 1.3 核心原则

1. **可读性优先**：代码是写给人看的，其次才是机器执行

2. **统一大于个性化**：团队统一规范优先于个人编码习惯

3. **简单优于复杂**：拒绝过度设计、炫技式写法

4. **可自动化不人工**：格式、检查、格式化全部工具自动化落地



## 2 基础代码风格规范（遵循 PEP8 + 现代约定）



### 2.1 缩进与空白

1. 统一使用 **4 个空格缩进**，禁止使用 Tab

2. 行尾**禁止多余空格**

3. 二元运算符两侧统一加单个空格，括号、列表、字典内部**无多余空格**

4. 函数、类定义之间空两行，函数内部逻辑块之间空一行



### 2.2 行长度约定

1. 代码行最大长度：**88 字符（Black 官方标准）**

2. 注释、文档字符串最大长度：88 字符

3. 超长字符串、参数自动换行，禁止手动硬换行



### 2.3 命名规范（强制统一）

严格遵循分类命名规则，全项目统一：

1. **模块/文件**：小写 + 下划线，如 `user_service.py`

2. **变量/函数/方法**：小写下划线式，如 `get_user_info`

3. **类名**：大驼峰，如 `UserInfoService`

4. **常量**：全大写下划线，如 `MAX_RETRY_TIMES`

5. **私有变量/方法**：单下划线开头，如 `_parse_data`

6. 魔法变量、内置变量：禁止自定义重写



禁止：拼音命名、无意义缩写、大小写混用、大小写拼音混合命名。



### 2.4 导入规范

1. 导入顺序固定分组（Ruff 自动校验），分组间空一行：

 - 标准库导入

 - 第三方库导入

 - 项目内部模块导入

2. 禁止通配符导入 `from xxx import *`

3. 禁止循环导入

4. 尽量减少不必要导入，杜绝未使用导入



## 3 语法与编码最佳实践



### 3.1 基础语法

1. 优先使用 Python 3.9+ 现代语法（类型注解、简化容器类型等）

2. 优先使用上下文管理器 `with` 处理文件、链接、锁资源

3. 字符串拼接优先 f-string（项目统一约定）

4. 遍历优先使用 `for ... in`，禁止下标无意义遍历



### 3.2 类型注解（项目强制）

1. **所有对外函数、核心业务函数必须加类型注解**

2. 变量、返回值明确标注类型，复杂类型使用标准库泛型

3. 入口脚本、简单工具脚本可酌情简化，核心服务代码全覆盖

4. 配合 Mypy 做静态类型校验，禁止忽略明显类型错误



示例：

```python

def get_user_by_id(user_id: int) -> dict | None:

 pass

```



### 3.3 异常处理规范

1. **禁止裸 except:**，必须明确捕获指定异常

2. 禁止吞异常：捕获异常必须打日志、兜底处理、向上抛出三者其一

3. 业务异常与系统异常分层定义，统一项目自定义异常

4. 资源异常必须保证最终释放（finally / with）



### 3.4 代码复杂度控制

1. 单个函数尽量控制在 **50 行以内**

2. 禁止超长嵌套（嵌套层级不超过 3 层）

3. 复杂逻辑拆分子函数，单一职责原则

4. 杜绝重复代码，通用逻辑抽离公共工具类/方法



## 4 文档注释规范



### 4.1 文档字符串

1. 所有**模块、类、公共方法**必须编写规范 docstring

2. 统一使用 **Google 风格文档字符串**

3. 说明功能、入参、返回值、异常、示例（复杂方法）



### 4.2 单行注释

1. 复杂业务逻辑、特殊兼容逻辑必须加注释

2. 注释说明**为什么这么写**，而非代码做了什么

3. 禁止大量无意义注释、垃圾注释、过期注释



## 5 项目工程规范



### 5.1 目录结构

严格遵循分层架构：分层解耦、职责单一，禁止业务逻辑散落各处。

- `config/`：配置文件、环境配置

- `common/`：公共工具、常量、异常、通用方法

- `service/`：核心业务逻辑

- `models/`：数据模型、结构体、ORM 模型

- `api/`：接口入口

- `tests/`：单元测试、集成测试

- `main.py`：项目启动入口



### 5.2 工具强制规范

本项目强制启用自动化工程工具，所有代码提交必须通过校验：

1. **Black**：代码统一格式化（无争议、零配置统一风格）

2. **Ruff**：语法检查、规范校验、导入排序、代码异味检测

3. **Mypy**：静态类型检查

4. **Pre-commit**：提交前自动执行所有规范校验



### 5.3 版本与依赖规范

1. 依赖统一管理在 `pyproject.toml`

2. 禁止随意引入冗余依赖

3. 固定依赖版本，禁止模糊版本号

4. 新增第三方依赖必须组内对齐、登记



## 6 测试规范

1. 核心业务逻辑必须编写单元测试

2. 关键分支、异常场景必须覆盖测试

3. 禁止提交未测试、裸跑的核心代码

4. 测试代码同样遵循本项目编码规范



## 7 禁止事项（红线规则）

1. 禁止硬编码密钥、地址、账号、密码

2. 禁止提交调试残留代码（print、断点、临时注释代码）

3. 禁止私自修改基础框架、通用底层逻辑

4. 禁止跳过工具校验、强制提交代码

5. 禁止生产代码保留无效测试逻辑、死代码



## 8 附则

1. 本规范为项目强制规范，代码评审以本文件为标准

2. 所有新增代码必须完全符合规范，存量代码逐步迭代整改

3. 规范可根据项目迭代统一更新，个人无权自定义规则
